# Данные

## Форматы данных

Файлы лежат по `data/reteco/track2_recor/<домен>/`:

| файл | содержимое |
|---|---|
| `documents.jsonl` | корпус: `doc_id`, `content` (общий для обоих сплитов) |
| `benchmark_train.json` / `benchmark_dev.json` | список диалогов: `id`, `task`, `turns[{turn_id, query, answer, conversation_history, gold_doc_ids}]` |
| `qrels_train.txt` / `qrels_dev.txt` | TREC-qrels: topic, 0, doc, rel |

## Устройство данных (проверено на dev, 28 сентября 2026)

Диалог — это **декомпозиция одного поста Stack Exchange** (`original_query`,
~280 слов) в 3–5 коротких реплик (~18 слов каждая, чистый текст, без HTML).
`metadata.method = unified_bright_workflow`. Поля реплики:

| поле | что | можно ли использовать в поиске |
|---|---|---|
| `query` | текущая реплика | да |
| `conversation_history` | `Q: … A: …` для всех прошлых реплик, **включая ответы** | да — это и есть причина, почему B1 даёт ×2.4 |
| `gold_doc_ids` | золото | только для оценки |
| `answer` | золотой ответ **текущей** реплики | **нет** — таргет 2b/2c |
| `subquestion_reasoning` | инструкция аннотатора «какие документы искать» | **нет** до ответа организаторов |

На уровне диалога: `original_query`, `original_answer` — исходный пост и
ответ; тоже аннотация, не диалог.

Числа dev, 858 реплик: T1 211, T2 211, T3 211, T4 121, T5+ 104. Среди 647
реплик T2+ золото **совпадает с предыдущей репликой у 41 %** и **⊆ объединению
золота прошлых реплик у 70 %**.

Документы короткие: медиана 20 слов, p90 160, длиннее 512 слов — 0 %. Домены
из BRIGHT (biology, earth_science, economics, psychology, robotics,
sustainable_living) — чанки веб-страниц с путевыми id
(`insects_attracted_to_light/Phototaxis_0.txt`); новые домены (drones,
hardware, law, medicalsciences, politics) — целые ответы, длиннее (медиана
75–140 слов).

**Как устроен корпус новых доменов.** Он собран *по диалогам*: на каждый
диалог `ex_N` в корпусе лежат его золотые документы `<домен>_ex_N_doc_k`
(≈5), отобранные вручную отрицательные `_neg_k` (≈40) и отрицательные из
Google `_google_neg_k` (≈300). В law: 281 doc, 2258 neg, 17 488 google_neg на
55 диалогов; в train+dev — 50 из них, **5 диалогов в корпусе есть, а в
train/dev нет** — это, по всей видимости, скрытый тест. Отрицательные по
построению тематически близки к золоту (это результаты Google по близким
запросам), поэтому BM25 на этих доменах слабее.

**Утечка:** в пяти новых доменах `doc_id` содержит id диалога **и тип
документа** (`_doc_` золото, `_neg_`/`_google_neg_` отрицательный):
`law_ex_111150_doc_0` ↔ топик `ex_111150_turn_1`. Никакой модели `doc_id` на
вход не давать. Вопрос, сообщать ли организаторам — в NOTES.md.

## Формат сабмита

Шесть колонок, разделитель — пробел или таб:

```
ex_3025_turn_1  Q0  drones_ex_3025_doc_0  1  11.2284  my_system
```

Первая колонка для 2a и 2c — всегда `<conversation_id>_turn_<turn_id>`.
Для 2b и 2c дополнительно JSONL с полями `turn_id` и `answer`.

**Формат `doc_id` разный в разных доменах.** В drones и law это
`<домен>_ex_<n>_doc_<k>`, а в biology — путь вида
`insects_attracted_to_light/Phototaxis_0.txt`. Ничего не парсить из id и не
собирать его из частей: брать как есть из корпуса.

Проверка перед сдачей:

```bash
source scripts/env.sh
$PY vendor/RETECO/starter_kit/format_checker.py run.trec \
  --qrels data/reteco/track2_recor/law/qrels_dev.txt \
  --corpus data/reteco/track2_recor/law/documents.jsonl \
  --doc-key doc_id
```

`--doc-key doc_id` обязателен: по умолчанию проверялка ждёт ключ `id`, это
поле трека 1, и на треке 2 падает с `KeyError: 'id'`.

Проверяет шесть колонок, уникальность и возрастание рангов, невозрастание
скоров, существование id. Выходит с ненулевым кодом — годится для CI, но в
пайпе код берётся от последней команды: писать `${PIPESTATUS[0]}`, а не `$?`.

## Правила соревнования

- Подтрек, в который не вошёл, **не ранжируется**, а не получает ноль.
- Внутри подтрека, в который вошёл, пропущенные реплики получают ноль.
- Дубликаты id выбрасываются после первого вхождения, неизвестные — игнорируются.
- Поиск только по корпусу организаторов. Внешние коллекции подмешивать нельзя.
- Проприетарные модели и API можно, но всё перечислить в статье.
- Обучаться на train, dev держать как честную проверку.
